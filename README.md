# 順路走 — 後端骨架

輸入出發地、想吃什麼、交通偏好與預算，產生一份可以刪減、會即時重算花費的行程。

這一版把原本跑在 claude.ai 裡的原型，改成一個可以自己架、自己部署的網站：
**API 金鑰放在後端，前端只跟自己的伺服器講話。**

---

## 跑起來

```bash
npm install
cp .env.example .env      # 把 ANTHROPIC_API_KEY 填進去
npm run dev
```

打開 http://localhost:8787

金鑰到 [console.anthropic.com](https://console.anthropic.com) 申請。
不確定該填哪個模型 id，執行 `npm run models` 會列出你的金鑰現在能用哪些。

**如果你的金鑰是「綁定身分」的**（personal 或 service account key），還要填 `ANTHROPIC_WORKSPACE_ID`。
少了它每次請求都會被擋在 400，錯誤訊息會直接告訴你去哪拿。
ID 在 Console → Settings → Workspaces 的 ID 欄位，`wrkspc_` 開頭。

### 不用金鑰也想先看畫面

```bash
MOCK_PLAN=1 npm run dev
```

會用內建的假行程走完整條串流路徑 —— 一樣是逐站出現、一樣能刪減與重算費用，
但不呼叫模型、不花錢。假資料的店名都標了「（示範）」。

---

## 部署到 Render

repo 裡有 `render.yaml`，Render 會照它建，不用手動填一堆欄位。

1. Render → **New → Blueprint**
2. 選 `chitravel` 這個 repo
3. Render 會問三個 secret（`sync: false` 的那些），把 `.env` 裡的值貼進去：
   `ANTHROPIC_API_KEY`、`ANTHROPIC_WORKSPACE_ID`、`TAVILY_API_KEY`
4. **Apply**

其他設定藍圖裡都寫死了：新加坡機房（離台灣最近）、Node 22、
健康檢查打 `/healthz`、推 commit 就自動重新部署。

公開網址上兩個參數刻意調保守：每個 IP 每分鐘 **3 次**、快取 **15 分鐘**。
一份行程約 NT$2，這兩個值決定有人亂按時你會賠多少。

**免費方案會休眠。** 閒置 15 分鐘後停掉，下一個訪客要等 30–60 秒喚醒。
給幾個人試夠用；要給不特定的人看就得升級。

### 為什麼不是 GitHub Pages

Pages 只能放靜態檔。這個專案的 `/api/plan` 要跑 Node，而且金鑰**必須**留在
伺服器端 —— 放到前端等於把信用卡貼在原始碼上。

### 為什麼還沒上 Cloudflare Workers

Hono 本來就是為 Workers 寫的，但免費方案每個請求只有 **10 毫秒 CPU**，
而串流解析器掃一份 16KB 的回應大約要 20–80 毫秒，會被砍掉。
付費方案（$5/月）有 30 秒 CPU，綽綽有餘。
另外 `process.env`、`node:crypto`、記憶體快取與頻率限制都要改成 Workers 的寫法，
大約兩三小時的工。等確定有人要用再搬。

## API

### `POST /api/plan`

送出：

```json
{
  "from": "台中高鐵站",
  "to": "台北",
  "food": "義式料理",
  "date": "2026-09-08",
  "start": "09:00",
  "people": 2,
  "budget": 3000,
  "transport": ["高鐵", "捷運", "步行"],
  "needs": ["不吃辣", "要開發票"],
  "include": ["打卡景點", "私房景點", "雨天備案"],
  "notes": ""
}
```

成功：

```json
{ "ok": true, "cached": false, "ms": 24310, "trip": { "title": "...", "stops": [...], "extras": [...], "tips": [...] } }
```

失敗：

```json
{ "ok": false, "code": "invalid_json", "message": "這次回來的格式跑掉了，再按一次通常就好。" }
```

`code` 可能是 `bad_request` / `no_key` / `rate_limited` / `upstream_error` / `invalid_json` / `empty_plan` / `timeout`。
前端照 code 顯示自己的文案，不直接吐後端訊息給使用者。

### `POST /api/plan/stream`

同樣的請求格式，但用 SSE 逐段回傳。**前端走的是這一支。**

模型是照順序把 JSON 寫出來的，所以一站寫完就能先送給前端，不必等整份寫完。
成本與一次給完完全一樣 —— 只有一次模型呼叫，差別只在把等待攤開來看：
第一張卡片大約 5 秒出現，而不是盯著轉圈圈等 40 秒。

事件：

| event | data | 時機 |
|---|---|---|
| `meta` | `{title, summary}` | 標題與摘要都寫完時 |
| `stop` | 一個 stop 物件 | 每寫完一站 |
| `extra` | 一個 extra 物件 | 每寫完一個備選 |
| `done` | `{tips, cached, ms, verifying, mock?, partial?}` | 行程寫完，`verifying` 是接下來要查證幾站 |
| `verify` | `{index, candidates, failed?}` | 每查完一站 |
| `end` | `{}` | 全部結束（含查證） |
| `error` | `{code, message}` | 出錯，前端照 code 顯示文案 |

`partial: true` 表示收尾解析失敗，但已經送出去的那幾站仍然有效 —— 前端不會因此把整頁清掉。

### 多天行程

`days` 是 1（當日來回）到 3。每個 stop 帶 `day` 欄位，前端據此在每天開頭插分隔線
並顯示當天小計。`days > 1` 時 prompt 會強制安排住宿，並要求住在隔天行程的起點附近 ——
不然使用者早上得先花一小時通勤。

`costUnit: "每晚"` 的金額是**每人每晚**（已按人數分攤），這樣加總不用猜一間房住幾個人。

上限訂在 3 天，是因為現在一趟只呼叫模型一次：天數愈多輸出愈長，
三天大約要三到四分鐘。要做更長的行程得改成**一天一次呼叫**，
讓第一天先出現、後面幾天邊等邊生 —— 那是下一步，不是現在。

### 多語言（繁中 / English / Français / 日本語）

右上角切換，選擇記在 `localStorage`。首次進站依 `navigator.languages` 判斷：
中文一律走繁中，日文、法文各自對應，**其餘一律英文** ——
對看不懂中文的旅客來說，英文比繁中好得多。

介面字串全部收在 `public/index.html` 的 `I18N`，四種語言 112 個鍵一一對齊
（有腳本可驗，缺鍵會直接顯示 `undefined`）。交通／條件／要包含這三組選項用
**索引**記住勾選狀態，切語言時文字變、選擇不變。

語言也一路傳到後端：

| 用途 | 做法 |
|---|---|
| 行程內容 | `PlanRequest.lang` → prompt 指定輸出語言 |
| 地點自動完成 | `/api/places?lang=` → Places 的 `languageCode` |
| 定位反查 | `/api/whereami?lang=` → Geocoding 的 `language` |
| 查證候選的說明 | Haiku 抽取時指定語言，但 **name 保留中文原文** |

**外語版最要緊的一條規則：地名一定留中文原文。**
prompt 要求寫成「譯名（中文原文）」，例如 `Ximending (西門町)`、
`Blue Line / Bannan Line (板南線)`、`Exit 6 (6號出口)`。
旅客要拿這些字對照站內招牌、問路、給司機看 —— 只給譯名等於沒用。
金額一律留新臺幣，不換算（匯率每天在動，換算只會誤導）。

內建的示範行程只有中文，所以其他語言不顯示「看示範行程」按鈕。

### 出貨前的兩道檢查：捷運路網與營業時間

實測抓到的兩類錯誤，畫面上都看不出來，使用者會照著走過去才發現：

- 「從龍山寺搭**板南線**到中正紀念堂」—— 中正紀念堂不在板南線上
- 「**華西街夜市** 11:40」—— 夜市中午沒開

同一類捷運錯誤在三次不同的實測裡都出現過（高雄市議會、台北中正紀念堂、東門），
不是運氣問題，是模型對台灣路網的記憶就是不可靠。

**做法是「先給、再驗」**：

1. **先給** — `promptIndex()` 把目的地城市的真實路網塞進 prompt
   （台北約 960 字元、約 600 tokens，成本可忽略）。沒有捷運的城市不注入。
2. **再驗** — 行程出來後 `checkTransit()` / `checkHours()` 逐站比對，
   有問題就把警告掛在那張卡片上。

資料來自 PTX（TDX 的前身，**不需要憑證**），用 `npm run fetch:metro` 抓下來
存成 `src/data/metro.json`（12 條路線、237 個站名、33KB）。**內建而不是即時查**：
路網一年變不了一次，內建就零延遲、零相依，PTX 哪天退役也不影響跑起來的服務。

#### 車站改名

`RENAMED` 是手動維護的舊名 → 新名對照。API 只給現名，看不出改過，
但模型的訓練資料裡多半是舊名：

| 舊名 | 現名 | 站號 |
|---|---|---|
| 西子灣 | 哈瑪星 | O1 |
| 市議會 | 前金 | O4 |
| 技擊館 | 苓雅運動園區 | O9 |

（用 StationID + 英文名比對確認過是同一批站改名，不是新站。）

旅客照著找「市議會站」，月台上寫的是「前金」—— 這比搭錯線還難自己發現。

#### 轉乘敘述

線上第一次真跑就抓到一個誤報：

```
搭板南線往南港展覽館方向，至台北車站換乘淡水信義線往象山方向，在東門站下車
⚠ 東門站不在板南線上      ← 這句話是對的，它在講轉乘
⚠ 象山站不在板南線上      ← 「往象山方向」是終點站，不是行程站
```

兩個修正：先把 `往…方向` 這類終點站名剃掉再抓站；提到兩條以上路線時
視為轉乘，只檢查「每站至少在其中一條線上」，不逐條比對。

**已知盲點**：放寬之後，「繞去轉乘卻在原線下車」這種怪句子抓不到。
要抓到就得做逐段對應，而那正是誤報的來源 —— 寧可留這個洞。

#### 三個誤報，三個不同的 bug

v1.6 上線後跑一趟台北行程，跳出三個警告，**三個都是假的**：

```
⚠ 中和站不在板南線、中和新蘆線上（實際在：環狀線）
⚠ 市政府與松山不在同一條線上，需要轉乘
⚠ 市政府站不在松山新店線上（實際在：板南線、烏日文心北屯線）
```

一個一個拆：

1. **路線名裡包含站名。**「中和新蘆線」裡有「中和」，抓站的時候把它當成
   一個行程站。修法是先把所有路線名從文字裡剃掉，再抓站名。
2. **步行段被當成搭車段。** 那一段寫的是「步行 8 分鐘」，沒提任何路線，
   於是走到「頭尾兩站要在同一條線上」的分支。加 `onFoot` 判斷直接跳過。
3. **台北和台中都有市政府站。** `metro.json` 原本以站名為 key，兩個市政府
   合成一筆，於是台北的市政府「也在」烏日文心北屯線上。改成
   `${city}|${station}` 當 key。

修第 1 點時我自己又生了第四個 bug：把路線名從文字裡剃掉之後，才去那段
文字裡找「有沒有提到路線名」—— 等於親手把線索抹掉，每一段都變成「沒提路線」。
現在是**在剃之前**判斷提到哪些線，**在剃之後**抓站名。

```ts
const mentioned: string[] = [];
let body = noDirection;
for (const [key, l] of Object.entries(DB.lines)) {
  // 找線用剃之前的 noDirection
  if (names.some((n) => noDirection.includes(n))) mentioned.push(key);
  // 抓站用剃之後的 body
  for (const n of names) body = body.split(n).join(" ");
}
```

三個誤報、零個真警告，那一版的驗證器是**淨負值** —— 它讓正確的行程看起來
像壞的。這比沒有驗證器還糟，所以修完之後補了 17 條回歸測試，
上面三句原文都在裡面。

#### 再兩個誤報：站名藏在別的名字裡

v1.7 上線後又跑了台北、高雄、英文兩天一夜各一趟，抓到兩個新的：

```
⚠ 松山站不在板南線、文湖線、淡水信義線上   ← 句子裡的是「松山文創園區」
⚠ 駁二大義站不在橘線、紅線上（實際在：環狀輕軌）  ← 句子明明就寫了「輕軌」
```

第一個跟「中和新蘆線」是同一類：**站名是別的名字的一部分**。剃路線名治不了
場所名，於是改成**站名後面要真的接著「站」才算數** —— 「松山文創園區」的
「松山」後面接的是「文」，直接不算。代價是模型寫「搭板南線到西門」這種
沒帶「站」的句子會漏檢，這是刻意換來的。英文／日文／法文走同一條路：
介面語言不是中文時站名寫成「Ximen（西門）」，後面接的是右括號，也算。

第二個是資料缺一個別名。高雄的「輕軌」就是環狀輕軌，但 `aliases` 是空的，
驗證器讀不出這句話有提到第三條線，就用「每站至少在紅線或橘線上」去檢查
一個輕軌站。補上 `"KLRT:C": ["輕軌"]` 就好。

順手也收緊了改名警告：原本只要文字裡出現舊名就報，於是
「西子灣**風景區**」被說成「已改名為哈瑪星站」—— 風景區沒有改名，改的是車站。
現在要寫成「西子灣站」或「往西子灣」才報。

（`往西子灣方向` 這種**要**報：月台上的方向牌現在寫的是哈瑪星，
照著找「往西子灣」的月台會找不到。用 PTX 的 StationID + 英文名再確認過一次：
O1 哈瑪星 / Hamasen、O4 前金 / Cianjin、O9 苓雅運動園區 / Lingya Sports Park。）

線上實測的成績：台北一日 2 個警告 → 修完剩 1 個真的；高雄一日 3 個 → 剩 2 個真的
（一個改名、一個「13:00 進場停留 80 分鐘會超過 14:00 打烊」）；
英文兩天一夜 0 個警告，而那趟行程的捷運路線人工核對後**全部正確**。
回歸測試 25 條，上面每一句原文都在裡面。

#### 修一個生一個：「或」

補上「輕軌」別名之後，把六趟真實行程（71 站）拿新舊版跑一次對照，
才發現我用一個誤報換掉了另一個誤報：

```
⚠ 鹽埕埔站不在環狀輕軌上（實際在：橘線）
   原句：「從鹽埕埔站步行約 12 分鐘，或搭輕軌至駁二大義站」
```

補了別名，這句就變成「只提到一條線」，於是走進「所有站都該在這條線上」的分支。
但這句話講的是**兩種走法**：走路 12 分鐘，或搭輕軌。兩個站分屬兩條路徑，
各自都對，湊在一起看才像錯的。

所以句子裡出現「或 / or / ou / または」時，不做單線嚴檢。
71 站裡只有 2 站（2.8%）因此放棄嚴檢，而那 2 站正好就是誤報。

**這件事本身是個教訓**：改驗證器不能只跑手寫的測試句，會看不到自己新生的洞。
現在改法固定成——把手上所有真實行程的原句用新舊兩版各跑一次，
只看「消失了什麼、保留了什麼、新增了什麼」。這次的結果：

| | 舊版 v1.7 | 新版 |
|---|---|---|
| 警告總數 | 6 | 4 |
| 誤報 | 2 | **0** |
| 漏掉真警告 | — | 0 |

保留下來的四個都逐句人工確認過是真的：東門站不在松山新店線上、
兩個「往西子灣方向」的改名提醒、一個「13:00 進場停留 80 分鐘會超過 14:00 打烊」。

#### 搭幾站

高鐵班次接上之後跑一趟台中→台北，車次與票價都對，**四段捷運裡三段的站數是錯的**：

```
⚠ 西門到中正紀念堂（松山新店線）是 2 站，不是 1 站
⚠ 中正紀念堂到台北101/世貿（淡水信義線）是 5 站，不是 4 站
⚠ 台北101/世貿到台北車站（淡水信義線）是 7 站，不是 4 站
```

這種錯畫面上完全看不出來，而旅客是盯著月台跑馬燈數站的，數到第四站就下車。
路線名對、方向對、站名對，只有數字錯——前面的驗證器一個都抓不到。

站數當然是可以算的，但**不能用序號相減**。`StationOfLine` 給的 `Sequence`
是把支線接在主線後面編的：新北投 28、北投 21，相減得 7 站——實際上它們相鄰。
「從北投站搭新北投支線一站到新北投站」是台北行程裡再常見不過的一句，
這個錯法會把它判成誤報。

`StationOfRoute` 分得出支線（R-3 就是北投↔新北投兩站，G-3 是七張↔小碧潭），
所以改成把每條營運路線的相鄰關係併成一張圖，兩站之間走 BFS：

```
TRTC:R 北投→新北投          = 1 站   （序號相減會得 7）
TRTC:R 中正紀念堂→台北101   = 5 站
TRTC:G 七張→小碧潭          = 1 站   （序號相減會得 17）
```

主線上兩種算法答案一樣，差別只在支線——而支線正是會出錯的地方。

難的是「這個 N 講的是哪兩站之間」。做法是由左到右掃：碰到「N 站」時，
往前找最近的站當起點、往後找最近的站當終點，兩站要**恰好共用一條線**
（有提到路線名就再收斂到那條）才判斷，定不出來就放過。三道防呆：
「第一站」是序數不算、句子有「或」不算、站名認不出來不算。

跑進九趟真實行程（114 站）的結果：**新增 7 個警告，7 個都是真的，
零誤報**。同一批行程裡有 4 處站數是對的，驗證器一次都沒吵：

| 句子 | 實際 | 判定 |
|---|---|---|
| 高雄車站→美麗島「一站」 | R10→R9，1 站 | 不報 ✓ |
| 美麗島→巨蛋「五站」 | R9→R13，4 站 | 報 ✓ |
| 巨蛋→高雄車站「六站」 | R13→R10，3 站 | 報 ✓ |
| 鹽埕埔→信義國小「兩站」 | O2→O5，3 站 | 報 ✓ |
| 前金→鹽埕埔「一站」 | O3→O2，1 站 | 不報 ✓ |
| 劍潭→士林「一站」 | R15→R16，1 站 | 不報 ✓ |

高雄那個還連錯兩件事——「凱旋轉紅線往小港方向 3 站到美麗島」，
實際是 4 站，而且往小港是反方向。

prompt 那邊也補了一條：站數要照路網索引數過，數不出來就寫「約 10 分鐘」。
索引本來就是照路線順序排的，模型有材料，只是不會自己去數。

#### 真的開瀏覽器看畫面，才發現漏掉一半

資料層跑得再乾淨，也要看畫面。用瀏覽器實際跑一趟台北行程，
綠色的修正區塊**一次都沒出現**——但那趟裡有三段站數是錯的：

```
【東門站 → 北投站】     怎麼去：搭 16 站到北投站        實際 15
【淡水站 → 台北車站】   怎麼去：搭 27 站到台北車站      實際 18
【國父紀念館站 → 東門站】怎麼去：搭 1 站到忠孝復興站    實際 2
```

看出共通點了：**起點站寫在卡片標題裡，不在「怎麼去」裡**。
修正只讀 `howTo`，配不成對就整段放過。而「A站 → B站」正是這個 app
最常見的交通段命名方式——等於一大類錯誤從頭到尾都沒被碰過。

修法是把標題的起點當上下文一起丟進去，但只准改 `howTo` 那一段。
不能整個標題丟：「東門站 → 北投站」裡的北投會跟句尾的北投配成同一站，
判斷式看到頭尾一樣就放過了，所以只取箭頭前面那半。

#### 環狀線不碰

補上標題上下文之後，冒出兩個輕軌的修正。查了才發現高雄環狀輕軌
**是真的一個圈**（`StationOfRoute` 的首尾相接）：

```
駁二大義 → 愛河之心   順時針 13 站、逆時針 25 站
```

兩個都對，看你往哪邊搭。BFS 只會給比較短的那個，而句子寫的是「順時針方向」。
**報錯報錯了只是講錯一句話，改錯了是把錯的數字寫進行程裡，使用者不會知道。**
所以環狀線一律不判斷站數。

（台北環狀線目前資料上首尾沒接起來——大坪林↔新北產業園區還沒通——還算得出來。）

十一趟行程 139 站的最終成績：**修正 14 處、警告 13 個、殘留錯誤 0**。

#### 同一句警告只講一次

高雄那趟裡「往西子灣方向」出現在三個不同的交通段，就跳了三次一模一樣的
改名提醒。三次都是真的——但重複三次跟假警告一樣會讓人學會忽略。
改成一趟行程裡同一句警告只講一次。

到這裡回歸測試已經有 81 條，一直放在我的暫存目錄裡不是辦法。
現在在 `tests/`，`npm test` 一次跑完：

#### 線上跑的是哪一版

改完驗證器推上去，從外面看不出 Render 到底換版了沒 —— 生成內容每次都不一樣，
「沒跳警告」可能是修好了，也可能是這次模型剛好沒寫出那個句子。
所以 `/healthz` 多回三個欄位：

```json
{ "ok": true, "model": "claude-sonnet-4-5",
  "commit": "55a743b", "metro": "2026-09-06", "startedAt": "..." }
```

`commit` 來自 Render 自動注入的 `RENDER_GIT_COMMIT`，本機是 `dev`。
一行 `curl -s .../healthz` 就知道線上是哪個 commit、路網資料多舊、上次重啟是什麼時候。

#### 只在有把握時才報錯

兩個驗證器都寧可漏報也不誤報：認不出來的站名、看不懂的營業時間、
寫著「24 小時」的，一律放過。**使用者看到一堆假警告就會學會忽略所有警告**，
真的錯也跟著被忽略。

警告文案跟著介面語言走（`warn-text.ts`），但**站名與路線名一律保留中文原文** ——
那正是旅客要拿去對照招牌的東西。

### 台鐵與高鐵：真的班次

原本第 5 點的要求是「推薦台鐵跟高鐵必須是正確的時刻表跟班次」。
模型記得住「台北到台中有高鐵」，但記不住車次——它寫的 0832 多半不存在，
而旅客是拿著那個車次去售票機的。

資料一樣走 PTX（TDX 的前身，**不需要憑證**）。實測 2026-09 能拿到什麼：

| | 端點 | 可查範圍 |
|---|---|---|
| 高鐵 時刻表 | `v2/Rail/THSR/DailyTimetable/TrainDate/{date}` | 隔天起，約 28 天 |
| 台鐵 時刻表 | `v3/Rail/TRA/DailyTrainTimetable/OD/{o}/to/{d}/{date}` | 當天起，約 60 天 |
| 高鐵 票價 | `v2/Rail/THSR/ODFare/{o}/to/{d}` | 一直都有 |
| 台鐵 票價 | `v2/Rail/TRA/ODFare/{o}/to/{d}` | 一直都有 |
| **剩餘座位** | — | **✗ PTX 沒有這個端點** |

剩餘座位這件事要講清楚：`AvailableSeatStatus` 在 PTX 回 404，TDX 有但要憑證，
而且台鐵那邊本來就沒有這種資料。**所以「還有沒有票」目前做不到**，
與其顯示一個猜的數字，不如不顯示。

高鐵沒有 OD 端點，只能抓整天（156 班、263KB）自己過濾；快取 6 小時之後
第二次查是 174ms。台鐵有 OD 端點，直接查。

#### 三個踩到的坑

**高鐵沒有「高雄站」，那站叫左營。** 旅客和模型都會寫「高鐵高雄站」，
照字面查會查不到，然後整段班表靜靜消失——這種洞比報錯還難發現，
所以 `THSR_ALIAS` 把高雄、新左營都導到左營。

**`new Date("2026-09-20T00:00:00+08:00").toISOString()` 會被 UTC 拉回前一天**，
兩天一夜的回程日期算成同一天。改成純數字算日期，不碰時區。

**環島之星不單售車票。** 台鐵 `ServiceType: 4` 那兩班（車次 1、2）會排在
時刻表最前面，照著去買票會買不到。連同 `SuspendedFlag` 一起濾掉。

#### 做法還是「先給」

跟捷運路網一樣，把真實班次塞進 prompt（約 320 字元），並要求
「車次只能從這裡挑，沒給班表的路段就不要寫車次」：

```
【高鐵 2026-09-12 實際班次 — 這是權威資料，車次與時刻只能從這裡挑】
去程（台中→台北）：0612 09:00→09:59、1210 09:08→09:54、0616 09:32→10:33…
  票價：標準座 700、自由座 675（每人單程）
回程 2026-09-12（台北→台中）：1321 16:01→16:52、0841 16:11→17:15…
上面沒列到的路段不要自己寫車次，只寫怎麼搭與大約需時。
```

日期超出可查範圍（例如三個月後的高鐵）時**只給票價**，並明講
「班表尚未開放查詢，不要寫車次與發車時刻」。票價是永遠查得到的，
給得出來的就給，給不出來的就說沒有——比讓它自己編一個像樣的車次好。

### 編輯行程與重排時間

行程出來之後可以直接改：每一站能移除／放回，站與站之間有「＋ 在這裡插入一站」。
手動插的站標成 `unverified` —— 我們對它一無所知，不假裝知道。

**一旦編輯過，時間就失準了。** 刪掉一站，後面所有站的時間原本不會動 ——
這是先前版本的實質缺陷。現在編輯後會亮出提示與「重排時間」鈕，
按下去打 `POST /api/replan`。

那支端點刻意做得很窄：

- 只送**站序**回去，不送整份行程
- prompt 明令「不准增刪站、不准換地點、不准改價格」
- 回來只套用 `time` / `duration` / `howTo` / `day` 四個欄位，
  **名稱、價格、備註一律沿用使用者手上那份** —— 重排就該只動時間，
  模型順手改掉別的欄位是最惱人的事
- 陣列長度對不上就整批不套用
- 排不下時模型要在 `note` 直說（「最後一站會趕不上末班車」），不准硬塞

### 我的行程：存檔、匯出、匯入

行程存在 **`localStorage`**，不是雲端 —— 換一台裝置就看不到。這是刻意的：
Render 免費方案沒有持久磁碟，做「分享連結」得先有資料庫。
要跨裝置就用「匯出檔案」，那份 JSON 同時也是備份。

存的是「可以還原的最小集合」：站序、時間、價格、備註、**以及哪幾站被移除了**。
查證回來的候選不存 —— 那是會過期的東西，下次打開重查比較誠實。

| 按鈕 | 做什麼 |
|---|---|
| 儲存 | 存進瀏覽器，左側「我的行程」看得到（最多 30 筆） |
| 匯出檔案 | 下載 `.json`，可備份、可搬到別台、可再匯入 |
| 匯入檔案 | 讀回 `.json`，順便存進清單 |
| 加入行事曆 | 下載 `.ics`，每一站一個事件（沒填日期時不顯示這個鈕） |

`.ics` 只收有時間的站 —— 硬塞一個假時間進行事曆比不加更糟。
折行照 RFC 5545 的 75 位元組規則處理，不然中文長行會讓某些行事曆解析失敗。

### 列印 / 下載 PDF

不裝任何 PDF 套件，也**不在伺服器上跑 Chromium**。

伺服器端產 PDF 單次尖峰要 300–400MB，而 Render 免費方案只有 512MB ——
兩個人同時按就會把整個服務打掛。為了一個按鈕賠上全站不划算。

「下載 PDF」按下去開瀏覽器的列印視窗（選「儲存為 PDF」；手機是分享→儲存到檔案）。
**瀏覽器的列印引擎本來就是這裡最好的 PDF 產生器**：中日文完美、版面由 `@media print`
控制、檔案小、離線也能用。升級到付費方案之後再換成真正的一鍵下載。

列印時收掉表單、工具列、費用列、插入鈕與訂房按鈕；卡片加 `break-inside: avoid`
不讓一站被切成兩頁。來源連結在紙上點不了，也一併隱藏。

### 地圖連結

每一非交通站都有「地圖」與「導航」。導航是**從上一站出發**算的 ——
使用者要的通常不是「這在哪」，而是「我人在上一站，怎麼過去」。
勾了自行開車就用 `travelmode=driving`，否則預設 `transit`。

**勾了自行開車才會多出「附近停車」。** 這顆刻意不接 Places API：
Google 地圖本來就有停車場圖層，有位置、營業時間，部分還顯示費率 ——
我們自己抓回來的資料會**更少而且要付錢**。一顆連結把使用者送進
Google 的搜尋結果，拿到的比自建的多。

（停車**價格**本身還是拿不到：Places API 沒有這個欄位，TDX 只有部分縣市有費率。
我不會編一個假價格填進去。）

### 住宿為什麼不給店名

模型對「哪家旅館現在還在營業、房價多少」幾乎沒有把握，所以誠實原則會讓它回 `generic`。
而查證也救不了：旅館的搜尋結果幾乎都是 Booking、Agoda 那類訂房網，頁面是動態產生的，
抓回來是空殼，抽不出可用店名 —— 餐廳有部落格食記可以抓，旅館沒有對應的東西。

所以 `kind: "stay"` 的站**不送查證**（省一次搜尋加一次萃取），
前端改成給一組「條件已經帶好」的訂房搜尋連結：城市 + 行政區、入住/退房日期、人數
都組進網址，使用者點過去就是已經篩好的結果頁。

房價與空房每天在動，給一個可能已停業的旅館名字，不如讓人去看即時的。

> 之後要做分潤，在 Booking 網址加上 `&aid=<你的聯盟編號>` 即可，使用者體驗完全不變。
> 這大概是這個產品最自然的第一條變現路徑。

### `GET /api/places?q=&session=`

地點自動完成，**代理** Google Places API (New)。金鑰只在後端用，不會出現在網頁原始碼裡。
只回台灣的地點（`includedRegionCodes: ["tw"]`），語言 `zh-TW`。

回 `{ok, suggestions:[{main, secondary, text}]}`。選定時填的是 `main`（「台中高鐵站」），
不是完整門牌 —— 好讀，而且模型本來就認得站名。

前端每打一個字停 260ms 才問一次，並帶 `session` token 讓 Google 以 session 計價。
沒設定 `GOOGLE_MAPS_API_KEY` 時回 `code: "no_google"`，前端據此關掉下拉、退回純文字輸入 ——
**這條路徑一定要能走，不能因為沒有金鑰就整頁壞掉。**

### `GET /api/whereami?lat=&lng=`

把瀏覽器拿到的經緯度反查成「市 + 區」。回傳刻意不給完整門牌 ——
行程規劃用得上的是「台南市中西區」這種粒度。

## 幾個刻意的決定

**表單先驗證再花錢。** `PlanRequestSchema` 擋掉的請求一個 token 都不會用到。

**模型回來的東西全部走 schema，而且全部 `catch`。** 模型少給一個欄位、把 `cost` 寫成字串，不該讓整份行程掛掉 — 該欄位退回預設值，其他照常顯示。

**prefill `{`。** 讓模型直接從左大括號開始寫，省掉「以下是為您規劃的行程：」這種開場白，也降低解析失敗率。

**快取用「條件 + 模型」當 key。** 開發期反覆按同一組條件測版面時，這個省下的錢比想像多。

**模型不准編店名。** 實測發現最危險的錯誤不是搭錯捷運線，而是行程裡出現一家
「名字是真的、但地點、類型、營業時間全錯」的餐廳 —— 使用者照著走過去會白跑一趟。
所以 prompt 要求每個 stop 自評 `verified`：

| 值 | 意思 | 前端顯示 |
|---|---|---|
| `landmark` | 捷運站、公園、園區、美術館這類長期存在的公共地標 | 不標 |
| `generic` | 沒有指名，只給「區域＋類型＋怎麼挑」 | 灰色虛線「未指名 · 到場再挑」 |
| `unverified` | 指名了具體商家，但沒查證 | 橘色「店名未查證」 |

模型漏填時一律當成 `unverified`，寧可多提醒一次。
這個欄位同時是下一步「接搜尋驗證」的介面：查到了就把 `generic` 補成真名並升級，
查不到就維持模糊。**模糊但正確，比精確但錯誤有用得多。**

**查證只查該查的，而且不讓模型碰網址。** 行程送完後，只有模型自評為 `generic` 或
`unverified` 的站會去搜尋（地標與交通段不浪費搜尋費）。防止它再編一次的兩道防線：

1. 抽取用的提示只給搜尋結果與**編號**，模型回傳 `source: 2` 這種編號，網址由後端依編號對回去 —— 模型碰不到網址，也就編不出網址。
2. 回來的店名必須逐字出現在搜尋結果原文裡，否則直接丟掉。
3. 地區要對得上這一站的 `area`，否則丟掉。搜尋很常回「全市美食懶人包」，
   裡面的店散落各區 —— 實測「五福商圈」查到的三家有兩家在左營與三民，
   不濾掉會害使用者走冤枉路。比對用的是去掉「區／商圈／老街」後的核心詞
   （`鹽埕區`→`鹽埕`、`五福商圈`→`五福`），短於兩個字就放棄比對，寧可不濾也不要濾錯。

查到的候選會掛在該站底下，每一筆都附「來源」連結。**使用者點一下就能自己確認** ——
這比假裝很準然後害人白跑一趟好得多。找不到就誠實說找不到。

**錯誤碼與錯誤訊息分開。** 後端給 code，前端決定要跟使用者怎麼說。

**串流解析自己走一遍字元，不靠正則抓物件。** 店名裡可能有 `{`、`}` 或跳脫引號，
必須追蹤字串狀態才不會把物件邊界抓錯。已經用隨機切片測過（每次切在不同位置，事件不重不漏）。

**模擬模式走的是同一條路徑。** `MOCK_PLAN=1` 也經過同一個解析器與同一組 SSE 事件，
所以測到的是真的那條路，不是另外寫一份假的。
